# CI/CD, taken apart

An illustrated, interactive guide to how **continuous integration and continuous delivery** work.

Instead of boxes and arrows, the pipeline is drawn as a bench-top production line. You push a commit and watch it travel from station to station. It gets built, tested, packaged, deployed and monitored, and rolled back if something goes wrong in production.

## Viewing the site

Open `index.html` in a web browser (Chrome, Safari, Firefox or Edge). There is no server, no install and no network access.

```sh
open index.html          # macOS
```

Keep `index.html` and `app.js` together in the same folder: the page loads its code from `app.js`.

Some viewers don't run JavaScript, such as editor previews, Quick Look and email attachments. They show the page without its figures. Open it in a real browser to see it move.

## What's on the page

### The line (Fig 1)

One large animated figure of the whole pipeline. Each station is a real machine standing in for one stage:

| # | Stage | On the line | What it teaches |
|---|---|---|---|
| 01 | Commit | A magazine of blanks with an exit gate | A push triggers a run for one exact commit, identified by its hash |
| 02 | Build | A hydraulic press | A deterministic build on a clean machine |
| 03 | Test | A gauge bridge with a probe and dial, a kicker and a reject bin | Automated checks against a tolerance. A failure stops the line and production stays untouched |
| 04 | Package | A crate dispenser and a labeler | An immutable, versioned artifact: build once, deploy many |
| 05 | Staging | A gantry crane and a staging table | The same artifact is smoke-tested in a production-like environment |
| 06 | Deploy | Two production bays and a router lever | Blue/green deployment: deploy to the idle bay, then switch traffic |
| 07 | Monitor | An error-rate dial with a red mark at 1 % | Watching real traffic after a release |
| 08 | Rollback | The lever flipping back | Instant rollback to the previous version, which is still running |

A row of status lamps along the front edge shows each stage as running (amber), passed (green) or failed (red), like a CI dashboard.

**Controls under the figure:**

- **Push a good commit:** the change passes every station and goes live.
- **Push a commit that breaks a test:** the gauge reads out of tolerance and the part is rejected. No artifact is made.
- **Ship a hidden regression:** the change passes its tests and staging, then the error rate climbs in production and the line rolls back.
- **Station buttons 01–08:** highlight one station and dim the rest.

A push made while a run is in progress waits in a queue, as it would on a real CI server. When nobody is interacting, an idle tour cycles through good, failing and rolled-back runs.

### The article

Each of the eight stations has its own section with:

- an **animated close-up** (Fig 2–9) that loops that station's part of a run;
- a plain-language explanation;
- **"In real pipelines"**: the commands and tools that do the same job (`npm test`, `docker push`, `kubectl rollout undo`, and so on);
- a practical tip.

After the stations, the page has:

- the whole line written as a **GitHub Actions workflow** (pull-request checks, least-privilege permissions, image pushed and deployed by digest, a production concurrency lock), with comments numbered to match the stations;
- **Choosing a deployment strategy:** recreate, rolling, blue/green, canary and feature flags compared;
- **Databases:** why rollback can't undo a schema change, and the expand/contract pattern;
- **Securing the line:** OIDC instead of stored keys, least privilege, pinning, scanning, SBOMs, signing and provenance;
- **Measuring the line:** the four DORA metrics;
- six rules the line follows;
- a short quiz;
- a glossary.

## Accessibility and preferences

- **Theme:** light by default. The ◐ button in the header switches to dark, and the choice is remembered.
- **Reduced motion:** if your system asks for reduced motion, the figures show still frames and stop looping.
- **Screen readers:** run results are announced through a polite live region, and the figures have text descriptions.
- **Keyboard:** every control is a regular button and can be reached with the keyboard.
- **Phones:** the main figure pans sideways and follows the action.

## Building from source

The page is generated by a Node script (Node 18 or newer, no npm packages needed):

```sh
node build.mjs          # writes index.html and app.js (light theme)
node build.mjs --dark   # the same page, dark by default
```

### Project layout

```
build.mjs            builds index.html and app.js
figure/
  model.mjs          the pipeline model: plans each run as keyframed tracks, so every
                     lamp, reading, version and moving part comes from one source
  geometry.mjs       the isometric drawing of the line, built once
  live.js            runtime for the main figure: draws poses, runs the tour, the
                     push queue and station highlighting
  minis.js           the per-section close-ups: a copy of the line framed on one
                     station, looping that station's part of a run
site/
  content.mjs        article text, workflow example, glossary, quiz and page CSS
  page.js            theme toggle and the "Show on the line" buttons
kit/                 the vendored anatomy isometric drawing kit (MIT, see kit/LICENSE-anatomy)
```

### Changing things

- **Text:** edit the `STEPS`, `YAML`, `GLOSSARY`, `STRATEGIES` and `QUIZ` constants (the extra topic sections are in `article()`) in `site/content.mjs`, then rebuild.
- **Timing and physics:** belt and crane speeds, the test tolerance and the rollback threshold are in `PHYS` in `figure/model.mjs`.
- **Close-ups:** each section's framing and loop times are in the `MINIS` table in `build.mjs`.

## A note on accuracy

The line is a teaching model. Times are compressed: a run takes about 35 seconds here, while real pipelines take minutes. Real pipelines also run stages in parallel and handle many commits at once. The concepts (gating on tests, immutable artifacts, staging, blue/green deploys, monitoring and rollback) match how production CI/CD systems work. Blue/green is shown because it is the easiest to see. Rolling updates and canaries are just as common, and the page compares them.
